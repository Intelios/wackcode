# Security boundaries

These are product guarantees, not implementation details. Don't weaken any of them. If a change seems to need to, stop and raise it instead.

## Network

No telemetry, account, backend, updater, or traffic on launch or on a timer. The app contacts only:

- provider endpoints the user configured, when a chat or a settings test asks for it, and the title model's connection (Settings › Providers › Automatic titles) once when a chat starts, while titles are on;
- the user's Git remote, only when they push;
- the chat's own provider when a command the agent started in the background reports while the chat is idle (a wake): at most three in a row before the user writes again, never after they stopped the chat's last run.
- public web pages the agent reads with `web_fetch` (on by default; its switch is in Settings › Tools), only when a chat asks. Every connection goes through `wack-web/src/guard.rs`: http or https only, never a URL with credentials in it, never loopback, private, link-local, carrier-grade NAT, multicast or reserved addresses (checked on the addresses DNS returns, so rebinding can't slip past, and again on every redirect), no cookies, no credentials and no proxy.
- the active search provider's own endpoint (Settings › Web), when the agent searches, when Test search runs, or, with "Read pages through" on, when the agent reads a page; the page's URL passes the same public-address check before it is sent. Redirects are refused, so a key never reaches another host, and a key goes only over https except to this Mac. A provider's key is `search:<id>` in `secrets.json`, or a DeepSeek connection's own key used only on `api.deepseek.com`; the search client never reads either back.
- the URLs of the HTTP MCP servers the user adds (Settings › MCP servers), when a chat in a project the server reaches uses it, or Test connection runs. The user's headers go only to that server's own origin: redirects are followed by hand only within it (at most five), a legacy SSE server's message endpoint must be on it too, and there is no proxy and no cookie jar. Headers go over https only, except to this Mac.

- pages opened in the browser (`wack-browser`, WackCode's bundled Chromium through CEF; [cef.md](cef.md)). Chromium starts the first time a tab is shown or used, never at launch, and quits with the app (its library is loaded at launch, which starts no process and makes no request; [cef.md](cef.md)). A chat whose saved layout has the Browser pane open shows its tab when the chat is opened, so opening that chat starts Chromium and loads that tab's saved address again. The user may open any address. The agent's navigations, and the redirects, script navigations and popups that follow while it drives a tab, pass `wack-browser/src/policy.rs`, and so does every other request a page makes while the agent drives its tab (frames, images, scripts, `fetch`, WebSockets: `WackResources` in `cef.rs`, checked on Chromium's IO thread before the request leaves): http or https only, never a URL with credentials in it, public addresses plus this Mac (loopback, `localhost`, `*.localhost`), and never other private, link-local, carrier-grade NAT, multicast or reserved addresses, judged on the addresses DNS returns. Chromium then looks the name up again itself, so unlike `web_fetch` this check cannot rule out DNS rebinding. Chromium's own services are off (`QUIET_SWITCHES` and `DISABLED_FEATURES` in `wack-browser/src/cef.rs`) and the hosts of those that ignore their switches (the component updater, network time) are mapped to nowhere (`BLOCKED_HOSTS`): idle, it contacts no host (checked with a net log, 2026-11-17). DevTools is reached only inside the process; there is never a remote-debugging port or pipe. The agent's downloads are refused. A tab the user opened is used by the agent's tools only while its address passes the same rule, and using it makes the agent its driver until the user acts in the pane. `browser_preview` (`wack-core/src/preview.rs`) starts nothing but the project's own Run command, the one the user set for the Run button, through the same `Runner` (in the project folder, provider keys removed from its environment), and opens only an address on this Mac that the command printed, or `localhost` at the port the agent names; a LAN address in its output is never offered.
- nothing for computer use (`wack-computer`): it reads and drives apps on this Mac and adds no origin. Its pictures and the text it reads reach the chat's provider like any other tool result.
- nothing for canvases (`wack-canvas`): a canvas adds no origin. Its pages are agent-written HTML that Chromium renders from `https://<site>.canvas.invalid/`, a name that resolves nowhere (`NOWHERE_HOSTS`), answered inside the process by the canvas's own `Site` (`wack-browser/src/site.rs`, `WackSiteResources` in `cef.rs`), which serves only that canvas's pages and copied assets. Canvas pages are never `browser_*` tabs and never saved. What keeps each kind of traffic offline:
  - requests and navigations (documents, frames, images, styles, fonts, `fetch`, `<form>`): refused natively before they leave (`on_before_browse`, `on_before_resource_load`), and by the CSP each response carries (only the page's own origin, `data:` and `blob:`). Popups, dialogs and downloads are refused too.
  - WebSockets, which Chromium never shows to the resource hooks: site pages share their own in-memory request context whose every connection goes to a proxy that resolves nowhere, loopback included (`make_site_context` in `cef.rs`), and the CSP's `connect-src 'self'`.
  - WebRTC, which the CSP does not cover: only that context's `webrtc.ip_handling_policy` (`disable_non_proxied_udp`), so with no working proxy a page gathers no candidates. Without it a canvas page reached a public STUN server, so this setting must never be dropped.
  - A context whose settings did not take is never used, and then no canvas page opens.

  Checked 2026-11-18 in the dev app, with the CSP removed: images, stylesheets, frames, `fetch` (public and loopback), navigations and WebSockets (public and loopback) all failed, and an `RTCPeerConnection` with a public STUN server gathered no candidates (a control run without the policy gathered `srflx`). A net log of the run showed no connection from a canvas page, and no lookup of the page's `dns-prefetch` and `preconnect` hosts; the only other socket was Chromium's own IPv6 check, a UDP `connect()` to Google Public DNS that sends no packet.

Never add a network origin silently. Call it out explicitly, and list it here.

## Credentials

- API keys persist only in `secrets.json` (mode 0600) in the app's data folder.
- A key travels from `secrets.json` to the request that needs it and nowhere else, with one path the user asks for: Settings › Providers' eye can show a saved connection's own key in its key field, through `Store::reveal_connection_key` (`wack-core`), until it is hidden again or Settings closes. A search provider's key has no such path. Either way a key never reaches `state.json`, a session file, an environment variable, a command line, a log, an error message or the usage ledger.
- `Store::provider` (`wack-core`) reads a key and hands back the provider that sends the requests. `Store::reveal_connection_key` is the only other read, and only for the connection the editor is showing.
- A key is never a command-line argument. `wack connect` asks for it at a hidden prompt, or reads it from a pipe.
- Processes the agent starts (`bash`, `watch`, Run and Build) and stdio MCP servers have provider key variables removed from their environment (`SECRET_ENV` in `wack-agent/src/tasks/mod.rs`). `bash` and MCP servers start from the user's login-shell environment (`wack-agent/src/shell_env.rs`), read once at launch, before those variables are removed.
- An MCP server's header and environment values are its credentials: `mcp:<id>` in `secrets.json`, never in `state.json` and never shown again in Settings (a blank field keeps the saved value). They leave `secrets.json` only in the `ServerSpec` a run or Test connection is given (`wack-core/src/mcp.rs`): headers on requests to that server's origin, variables to that server's own process and no other. Every MCP error and the stderr tail is redacted of them (`ServerSpec::redact`), and a tool list that contains one is never written to the catalogue cache (`v3/mcp-cache/`, declarations only, 0600).
- The browser's profile (`v3/browser/profile` in the app's data folder, mode 0700) holds the sign-ins and site data of the pages the user opens: a credential store of its own, kept apart from `secrets.json`. Chromium's Keychain encryption is off (`use-mock-keychain`, the owner's call on 2026-11-17: the ad hoc signed app was asked for the Keychain again after every rebuild, and the browser's network hung until it was answered), so the folder's permissions are what protect it, as 0600 protects `secrets.json`. It is never read from or written to another browser's profile. Each chat's open tabs (address, title, who opened them) are kept in `state.json` like its title and layout; an address can carry whatever its site put in it, so they are as private as the rest of that file. API keys never enter the browser: not in its environment, its command line or a script injected into a page. Settings › Browser › Clear browsing data deletes the profile folder: at once if Chromium hasn't started; otherwise every cookie at once (CEF's cookie manager) and the folder at the next launch, before Chromium can start (`cef::finish_clearing`, marked by `browser/clear-profile`), because Chromium cannot start twice in one process.
- What the agent's browser tools (`wack-browser/src/tools/`) hand the model, which then reaches its provider: page outlines, page text, screenshots, console lines and the request list (addresses, statuses, sizes) of the tabs it uses. Password, one-time-code and card fields show `[redacted]` in outlines (`snapshot.rs`); page text leaves out form values, though a page that prints a secret on screen shows it in text and screenshots. No tool returns cookies or storage. Running a script (`browser_eval`) and reading a response body (`browser_network`'s `body_of`) could read a site's script-visible cookies, storage and authenticated responses, so they work only on pages and requests on this Mac (`policy::is_this_mac`: the user's own dev servers), never on the open web (the owner's call, 2026-11-18). A file input gets only files inside the chat's project folder (`browser_upload`).
- Pictures reach the model's provider like any other tool result: screenshots, image files `read` opens, MCP images and `read_image`'s reopened ones. Each original is kept for the chat in its `images/` folder (`wack-agent/src/images/store.rs`, 0600 in a 0700 folder, deleted with the chat) and never leaves it except as a viewing copy in a request.
- Error text shown to the user or written to disk is redacted first: the HTTP client removes the key from any error a server echoes back.
- TLS trusts the system certificate store.

## The automation socket

`cargo dev` builds the app with the `automation` feature, which opens a local Unix socket that can read the UI and send it clicks and keys (see [testing.md](testing.md)). It exists so agents can check UI work.

- It is compiled only with the `automation` feature and only in debug builds. A release build cannot contain it.
- It listens only when `WACKCODE_AUTOMATION` names a socket path (`.cargo/config.toml` sets it for `cargo` runs only), and the socket file is made private (mode 0600) as soon as it exists.
- Its `computer` command runs a computer tool on the chat in front as its agent would, so it shows the same access card and is bound by the same rules (below); clicking the card's tags answers it, as a person at the screen would.
- It has no credential path of its own: no command returns a key. Its `browser` command drives the dev app's browser, whose profile is the dev data folder's own, never the installed app's. Like a person at the screen it can click Settings › Providers' eye (debug builds only), and then a screenshot shows what the eye shows.

## Reading project files

Project context files such as `AGENTS.md` load on purpose. Everything else the agent reads (files, tool output, web pages) is data, never instructions; the system prompt says so and no feature may undo that.

## Chat's scratchpad

A chat in the Chat area has no project. Its working folder is its own scratchpad, `v3/scratch/<chat>/` (mode 0700, deleted with the chat), and the agent's reach is cut to fit:

- **Its file tools stay inside the scratchpad.** `read`, `write`, `edit`, `ls`, `grep` and `find` get every path through `wack_tools::text::resolve`, which confines a Chat run (`ToolContext::confine`, set by `Profile::chat`) with `wack-tools/src/confine.rs`, ported from version 2's tested policy. It resolves `~`, absolute and relative paths and `file://` addresses, takes `.` and `..` out by their spelling, then compares *real* paths, so a symlink out (as a folder, a file or dangling), a sibling folder whose name starts with the scratchpad's, and a scratchpad that has gone are all refused; the tool then works on the location that was checked. `grep` and `find` never follow links while walking. It is a rule on the agent's tools, not a sandbox: a hard link something else placed inside is not seen.
- **No shell.** A Chat run has no `bash`, no background commands, no Build or Run, no sub-agents and no skills or slash-command templates (only the app's own `/new`, `/name`, `/copy`, `/compact`). Its registry is built from an allowlist (`wack-agent/src/chat_kit.rs`), and `ChatGuard` refuses any call to a tool off it.
- **The other ways to name a file**: `browser_upload` already takes only files inside the working folder, now the scratchpad (real paths). A canvas copies local images in only from the scratchpad or the chat's own saved pictures (`Canvases::confined`, `Store::confine_images` in `wack-canvas`), never from elsewhere on the Mac. The browser never opens `file://` (`policy.rs`); its rules are otherwise a Code chat's, loopback included. `read_chat` takes a chat id, never a path, and reads only the Chat area's other chats (`wack-core/src/chat_refs.rs`), so a project's conversation never reaches the Chat area. A scratchpad file chip in the transcript reveals its file in Finder only after the app checks its real path is inside that chat's scratchpad (`AppState::reveal_scratchpad_file`).
- **No instruction files.** A Chat chat's prompt is its persona and its guide only (`prompt::chat_system`): `AGENTS.md` and `CLAUDE.md` are not read, since walking up from a scratchpad reaches the user's home folder.
- **MCP servers** reach a Chat chat only when set to all projects, and start in one shared empty folder (`v3/chat-area/`), never a scratchpad, so no server is rooted where it could read one.

A Chat chat adds no network origin: its web, browser and MCP traffic is a Code chat's, under the same rules above.

## Computer use

The agent working in the user's other Mac apps (`wack-computer`). It is off until the user turns it on (Settings › Computer use), and each rule here is enforced in code, not asked of the model:

- **Code chats only.** A Code chat's run gets its tools (`RunSetup::computer`); the Chat area, `wack run` and sub-agents never do. Sub-agents are kept out three ways: the tools are registered after the children's share (`wack-core/src/run.rs`), copy children refuse the `computer_` prefix (`wack-agent/src/agents/child.rs`), and every tool refuses a call from a sub-agent (`ToolContext::caller`).
- **The user grants each app, from a card.** The first use of an app in a chat raises a card above the composer (Allow for this chat, Always allow, Deny, Never allow); the call waits, with no timeout, until the user answers or stops the run. Only that card's live id answers it (`ChatComputer::answer`): no tool can, and a stale id grants nothing. An answer is checked against the policy again, so a block added meanwhile wins. A denial lasts until the user's next message. Always allow is saved by bundle id and canonical path together, only while answering a live card (`Store::always_allow_app`), and Settings can only take it back, which takes back every chat's allow of that app.
- **Never controlled**, whatever the card says (`wack-computer/src/policy.rs`): every WackCode build (by bundle id, pid and path, so the dev app and the installed app never drive each other), terminals and script runners, installers, password managers and Keychain, security tools, system UI and System Settings, and the bundle ids the user never allows. Web browsers are look-only: windows, outlines and pictures, never input; the agent works on the web in its own browser.
- **WackCode is never looked at.** No WackCode window is pictured, outlined or targeted. Pictures are of one allowed app's window only.
- **Secrets stay unread.** A password field's value is never read, and typing, keys, focus and clicks into one are refused, as is typing while secure input is on anywhere. A clipboard item a password manager marks concealed or transient is never read.
- **The clipboard is asked for separately.** `computer_clipboard` asks on a card before it first reads the clipboard in a chat, and again before it first writes to it (Deny or Allow for this chat; nothing is saved), and Plan mode refuses it.
- **Text from apps is data.** It reaches the model between `<app-data>` markers carrying a fresh nonce, so an app's content can't close them, and the tool descriptions say not to follow instructions found there.
- **Window titles stay private.** `computer_apps` lists the windows of apps the chat may use only.
- **Files.** `computer_open` opens only files inside the chat's folder (real paths).
- **System chords are refused**: ⌘Q, ⌘Tab, ⌘Space, ⌃⌘Q, ⇧⌘Q, ⌥⌘Esc and the screenshot chords (`keys::system_chord`).
- **Permissions are asked only from Settings.** Allow… resets WackCode's own stale grant (`tccutil reset` with WackCode's bundle id, never another id or none) before macOS asks again; no tool call ever prompts or resets.
- **No timeout covers the card, and Stop takes it down.**
