# Security boundaries

## Network

The app has no telemetry, account, backend, updater, or launch/timer traffic. Provider traffic is limited to configured providers for chats, settings tests and Fetch models, the optional automatic-title connection once when a chat starts, and the background wakes described below. Git remotes are contacted only when the user pushes.

A command the agent started in the background may wake the chat's provider while the chat is idle: at most three times in a row before the user writes again, and never after the user stopped the chat's last run.

- Fetch models (Settings › Providers) sends one GET to the model list beside the address in the editor (`…/models`, Anthropic's paged), only when pressed, following redirects only within that origin. It sends the key typed in the editor, or the saved key only while the address is at the saved one's origin, or none.
- The model catalogue's Refresh (Settings › Providers) downloads `https://models.dev/catalog.json`, only when pressed: no key, cookie or anything about the user (a generic `WackCode/<version>` User-Agent), redirects refused, 60 seconds and 32 MB at most. What it brings is data that fills model rows; it never decides where a request goes. The snapshot built into the app needs no network.
- `web_fetch` (on by default; its switch is in Settings › Tools) fetches only public HTTP(S) pages when a chat asks. URLs with credentials and loopback, private, link-local, carrier-grade NAT, multicast, or reserved addresses are refused on the addresses DNS returns and on every redirect, so rebinding cannot slip past. It uses no cookies, credentials, or proxy.
- Web search contacts only the active search provider (Settings › Web) for agent searches, Test search, and optional “Read pages through” requests. Page URLs sent to that provider pass the same public-address check first. Redirects are refused so a key cannot reach another host, and keys travel only over HTTPS except to this Mac. A provider key is stored as `search:<id>` in `secrets.json`; a DeepSeek connection's own key is used only on `api.deepseek.com`. The search client never reads either key back.
- The bundled Chromium browser starts when a tab is first shown or used, not at launch, and quits with the app. Loading its library at launch starts no process and makes no request. Opening a chat whose saved layout includes a Browser pane reloads that tab's saved address. The user may open any address. Agent-driven tabs and every navigation or request that follows are limited to HTTP(S) URLs without embedded credentials, on public addresses or this Mac (loopback, `localhost`, and `*.localhost`); other private, link-local, carrier-grade NAT, multicast, and reserved addresses are refused on the addresses DNS returns. Chromium resolves the name again itself, so this check cannot rule out DNS rebinding.
- Chromium's own services are disabled or blocked, and idle Chromium contacts no host. DevTools is available only inside the process, never through a remote-debugging port or pipe. Agent downloads are refused. The agent can use a user-opened tab only while its address passes the same policy, and only until the user acts in the pane.
- `browser_preview` starts only the project's configured Run command, in the project folder with provider keys removed from its environment. It opens only an address on this Mac printed by that command, or `localhost` at the port the agent names; a LAN address in the output is never offered.
- Computer use adds no network origin. The app text and pictures it captures reach the chat's provider like any other tool result.

Never add a network origin silently; call it out explicitly and list it here.

## Credentials

- API keys persist only in `secrets.json` (mode 0600) in the app's data folder. They are read only to construct the provider that sends requests or for the explicit Settings reveal below.
- A key travels from `secrets.json` only to the request that needs it, except when the user asks Settings › Providers to reveal a saved connection's own key. The eye shows that key until it is hidden again or Settings closes; a search provider's key has no such path. A stored key never reaches `state.json`, a session file, an environment variable, a command line, a log, an error message, or the usage ledger.
- Provider requests follow redirects only within the origin of the address the user set (five at most), so a key never reaches another host; a redirect elsewhere is an error naming that host.
- Processes the agent starts (`bash`, `watch`, Run and Build) and stdio MCP servers inherit the user's login-shell environment, read once at launch, with provider-key variables removed before they start.
- An MCP server's header and environment values are its credentials, stored as `mcp:<id>` in `secrets.json`, never in `state.json`, and never shown again in Settings; a blank field keeps the saved value. Headers go only to that server's origin and variables only to its own process. MCP errors and stderr tails are redacted, and a tool list containing a credential is never written to the catalogue cache (`v3/mcp-cache/`, declarations only, 0600).
- The browser profile (`v3/browser/profile`, mode 0700) holds the sign-ins and site data of pages the user opens, separately from `secrets.json` and every other browser's profile. Chromium's Keychain encryption is disabled, so the folder's permissions protect it. API keys never enter the browser's environment, command line, or scripts injected into pages.
- Each chat's open tabs (address, title, and who opened them) are stored in `state.json`; addresses can contain sensitive site data and are as private as the rest of that file. Settings › Browser › Clear browsing data deletes the profile immediately if Chromium has not started. Otherwise it clears every cookie immediately and deletes the folder at the next launch, before Chromium can start, because Chromium cannot start twice in one process.
- What the agent's browser tools (`wack-browser/src/tools/`) hand the model, which then reaches its provider: page outlines, page text, screenshots, console lines and the request list (addresses, statuses, sizes) of the tabs it uses. Password, one-time-code and card fields show `[redacted]` in outlines (`snapshot.rs`); page text leaves out form values, though a page that prints a secret on screen shows it in text and screenshots. No tool returns cookies or storage. Running a script (`browser_eval`) and reading a response body (`browser_network`'s `body_of`) could read a site's script-visible cookies, storage and authenticated responses, so they work only on pages and requests on this Mac (`policy::is_this_mac`: the user's own dev servers), never on the open web (the owner's call, 2026-11-18). A file input gets only files inside the chat's project folder (`browser_upload`).
- Checkpoints (`wack-core/checkpoints.rs`) copy a chat's folder, as the project's `.gitignore` lets through, into `v3/checkpoints/<chat>/` (mode 0700, deleted with the chat) before each of the user's messages, so a rewind can put files back. A folder holding WackCode's own data folder, or the home folder, is never snapshotted, and the copies never leave the Mac. A `.env` the project does not ignore is copied like any other file.
- Pictures reach the model's provider like any other tool result: screenshots, image files `read` opens, MCP images, and `read_image`'s reopened ones. Each original is kept in the chat's `images/` folder (0600 in a 0700 folder, deleted with the chat) and leaves it only as a viewing copy in a request.
- Error text shown to the user or written to disk is redacted first; the HTTP client removes any key a server echoes back.
- TLS trusts the system certificate store.

## The automation socket

`cargo dev` builds the app with the `automation` feature, which opens a local Unix socket that can read the UI and send it clicks and keys (see [testing.md](testing.md)). It exists so agents can check UI work.

- It is compiled only with the `automation` feature and only in debug builds. A release build cannot contain it.
- It listens only when `WACKCODE_AUTOMATION` names a socket path (`.cargo/config.toml` sets it for `cargo` runs only), and the socket file is made private (mode 0600) as soon as it exists.
- Its `computer` command runs a computer tool on the chat in front as its agent would, so it shows the same access card and is bound by the same rules (below); clicking the card's tags answers it, as a person at the screen would.
- It has no credential path of its own: no command returns a key. Its `browser` command drives the dev app's browser, whose profile is the dev data folder's own, never the installed app's. Like a person at the screen it can click Settings › Providers' eye (debug builds only), and then a screenshot shows what the eye shows.

## Chat's scratchpad

A chat in the Chat area has no project. Its working folder is its own scratchpad, `v3/scratch/<chat>/` (mode 0700, deleted with the chat), and the agent's reach is cut to fit:

- **Its file tools stay inside the scratchpad.** `read`, `write`, `edit`, `ls`, `grep` and `find` normalize `~`, absolute and relative paths and `file://` addresses, then compare real paths to refuse traversal and symlink escapes; `grep` and `find` never follow links while walking. This is tool confinement, not an OS sandbox: a hard link something else placed inside is not detected.
- **No shell.** A Chat run has no `bash`, background commands, Build or Run, sub-agents, skills, or slash-command templates; only the app's own `/new`, `/name`, `/copy`, and `/compact` remain. An allowlist and guard refuse every other tool.
- **The other ways to name a file.** Browser uploads take only files inside the scratchpad, and a canvas copies local images only from the scratchpad or the chat's own saved pictures. The browser never opens `file://`; its other rules are a Code chat's, loopback included. `read_chat` takes a chat id, never a path, and reads only the Chat area's other chats, never a project's conversation. A scratchpad file chip reveals its file in Finder only after its real path is confirmed inside that chat's scratchpad.
- **No instruction files.** A Chat chat's prompt is its persona and its guide only (`prompt::chat_system`): `AGENTS.md` and `CLAUDE.md` are not read, since walking up from a scratchpad reaches the user's home folder.

A Chat chat adds no network origin; its web, browser, and MCP traffic follows the same rules as a Code chat's.

## Computer use

The agent working in the user's other Mac apps is off until the user turns it on (Settings › Computer use). Except for the prompt-injection mitigation noted below, these boundaries are enforced in code, not asked of the model:

- **Code chats only.** The Chat area, `wack run`, and sub-agents never receive computer tools.
- **The user grants each app, from a card.** The first use of an app in a chat raises a card above the composer (Allow for this chat, Always allow, Deny, Never allow); the call waits with no timeout until the user answers or stops the run, and Stop takes down the card. Only the live card can answer it; a stale id grants nothing, and an answer is checked against the current policy again. A denial lasts until the user's next message. Always allow is saved by bundle id and canonical path together only while answering a live card; Settings can revoke it, which takes back every chat's allow of that app.
- **Never controlled**, whatever the card says: every WackCode build (so the dev app and installed app never drive each other), terminals and script runners, installers, password managers and Keychain, security tools, system UI and System Settings, and the bundle ids the user never allows. Web browsers are look-only: windows, outlines and pictures, never input; the agent works on the web in its own browser.
- **WackCode is never looked at.** No WackCode window is pictured, outlined or targeted. Pictures are of one allowed app's window, or of the screen showing only the apps the chat may use.
- **The screen is the user's until they hand it over.** Background input goes to the app's process and never moves the user's pointer. Full-screen control (`screen: true`) takes the real pointer and keyboard only after the user allows it on a separate, unsaved card, for one chat at a time and until that run ends. Moving the mouse, pressing a key, or ⌃⌥⌘. (which also stops the run) gives it back at once, and it is not requested again before the user's next message. Every event is checked immediately before posting for continued screen ownership and a valid target in the app; a failed check stops the input and releases any held button. An accent glow around every display and a label at the top show that the screen is taken. Without the event tap watching the user's input, the screen is never taken.
- **The clipboard is asked for separately.** `computer_clipboard` asks on a card before its first read and again before its first write in each chat (Deny or Allow for this chat; nothing is saved), and Plan mode refuses it.
- **Text from apps is data, as a mitigation rather than a hard boundary.** It reaches the model between `<app-data>` markers carrying a fresh nonce so app content cannot close them, and tool descriptions say not to follow instructions found there. This reduces prompt-injection risk; it does not guarantee the model ignores malicious app content.
- **Files.** `computer_open` opens only files whose real paths are inside the chat's folder.
- **System chords are refused**: ⌘Q, ⌘Tab, ⌘Space, ⌃⌘Q, ⇧⌘Q, ⌥⌘Esc and the screenshot chords.
- **Permissions are asked only from Settings.** Allow… resets WackCode's own stale grant before macOS asks again, never another app's grant or all grants; no tool call ever prompts or resets.
