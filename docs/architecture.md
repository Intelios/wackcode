# Architecture

WackCode is one Rust process. There is no Node worker, no IPC protocol and no web UI. The browser engine adds Chromium's own helper processes through CEF, which is why the app runs from an `.app` bundle (assembled by `apps/xtask`; `apps/xtask/src/bundle.rs` holds the layout and its invariants).

Each file's header comment states its invariants; this is the map.

## Crates

```
apps/wackcode      the app binary: opens the window, hands it to wack-ui
apps/gallery       renders UI scenes to PNG files
apps/wackcode-helper  CEF's helper processes (renderer, GPU, utility), copied into the bundle
apps/xtask         assembles the .app bundles: `cargo dev`, `cargo xtask bundle`
crates/wack-ui     views, pane tree, layout solver, theme        (GPUI)
crates/wack-core   engine: projects, chats, settings, secrets, Git, PTYs, events
crates/wack-agent  turn loop, tool registry, prompt assembly, sessions, compaction
crates/wack-tools  read, write, edit, bash, grep, find, ls
crates/wack-web    web_fetch (and web_search), and the guard that keeps them on the public internet
crates/wack-browser  the browser engine: Chromium through CEF, each chat's tabs, the agent's address policy
crates/wack-canvas  canvases: the agent's HTML artboards, drawn offline by the browser engine; their tools, tweaks and comments
crates/wack-computer  computer use: the agent in the user's other Mac apps, through Accessibility, window pictures and input; its access rules
crates/wack-mcp    the MCP client: servers as deferred tools, connections shared per project
crates/wack-llm    provider wire formats, streaming events, usage, retries
crates/wack-catalog  the model catalogue: context, max output, efforts and vision from models.dev, bundled and refreshable
crates/wack-cli    `wack`: the agent without the app
```

Dependencies point downwards only: `wack-ui` → `wack-core` → `wack-agent` → `wack-llm`, with `wack-tools`, `wack-web` and `wack-mcp` beside the agent. `wack-browser` sits beside them too: `wack-core` hands a chat's `ChatTabs` to every run, and `wack-ui` lends the engine the window's view. `wack-canvas` sits on `wack-browser` and `wack-agent` the same way: a chat owns its `Canvases`, and `wack-core` hands them to every run. `wack-computer` sits beside them on `wack-agent`: the app owns one `Computer`, each Code chat owns its `ChatComputer` (grants, the access card), and `wack-core` hands it to the chat's runs. `wack-catalog` depends on nothing of ours: `wack-core/catalog.rs` keeps it on disk and fills model rows from it.

## The one boundary that matters

**Nothing below `wack-ui` may depend on GPUI.** The UI is a viewport onto the engine: it calls typed async commands and subscribes to typed event streams. That keeps the choice of UI framework confined to one crate, and it is why the agent can run and be tested with no window at all (`wack-cli`).

The engine runs on Tokio. `gpui_tokio` bridges the two, so a view can await engine work.

State lives in models, not views. Closing a pane or switching a tab must never lose a terminal's scrollback or a diff's selection.

## Where data lives

```
~/Library/Application Support/com.wackcode.desktop/     (.dev for the dev app)
  usage/v1/...              the TokenTrail ledger: a published contract, see wackcode-usage-v1.md
  v3/state.json             projects, chats, settings
  v3/secrets.json           API keys, mode 0600
  v3/sessions/<chat>.jsonl  one append-only file per chat
  v3/sessions/<chat>/<id>.jsonl  each of the chat's sub-agents (a1, a2…), removed with the chat
  v3/checkpoints/<chat>/    the chat's checkpoints: a shadow Git store of its folder before each of the user's messages (0700, removed with the chat)
  v3/tasks/<chat>/<id>.log  output of the commands the agent ran in the background (removed with the chat)
  v3/canvases/<chat>/<id>/  one canvas: canvas.json (its index), each artboard's HTML, assets/, comments.json, view.json (where the board's camera was left), renders/ (pictures, thumbnails, reports); removed with the chat
  v3/browser/profile        the browser's profile (0700)
  v3/backgrounds/          backdrop images
  v3/memory/<label>-<key>/  one project's memory notes (Markdown with frontmatter), origin.json, .trash/
  v3/memory/chat-c4a7c4a7c4a7/  the one memory store every Chat chat shares
  v3/scratch/<chat>/        a Chat chat's scratchpad, its only working folder (mode 0700, removed with the chat)
  v3/chat-area/             the one empty folder Chat chats' MCP servers start in
  v3/commands/<name>.md     the user's own slash commands (Settings › Commands)
  v3/agents/<name>.md       the user's own sub-agent roles (Settings › Sub-agents); the only agent folder WackCode writes to
  v3/web-usage.json         Settings › Web's monthly count of searches and page reads per provider
  v3/mcp-cache/<sha256>.json  each MCP server's last tool list, named by its connection's fingerprint (7 days)
  v3/model-catalog.json     the model catalogue as last refreshed from models.dev; used while newer than the built-in snapshot
~/.agents/skills/           the user's skills, shared with other tools; the only skill folder WackCode writes to
```

Everything of the app's own lives under `v3/`; version 2's files share the folder and are never read or written. Skills also load (read-only) from other tools' folders the user switches on (`~/.claude/skills`, `~/.codex/skills`, `~/.config/opencode/skills`) and folders they add; a project's own skill folders are never read. Sub-agent roles likewise load from Claude Code's `~/.claude/agents` when the user switches it on, read-only, and never from a project.

## The agent core

Each area's invariants are in its files' headers; these are the ones that span files.

- **`wack-llm`** turns one internal `Request` into three wire formats (`anthropic.rs`, `responses.rs`, `chat.rs`) and their event streams back into one `Response`. Blocks a provider needs back unchanged (thinking signatures, encrypted reasoning, its own tool-search blocks) travel as `Opaque` and are replayed only to the format that made them. `retry.rs` retries rate limits, overload and network failures, never once any text has reached the user. A request's `output_limit` is the model's max output: never sent on its own, it caps whatever is asked for. `testing.rs` is the scripted provider every test above this crate uses; `HttpProvider::list_models` reads a provider's own model list for Fetch models.
- **The turn loop** (`wack-agent/agent.rs`): every tool call gets exactly one result in the next message, whatever happens (refused, failed, stopped). Calls that only read run side by side, as do calls whose tool is marked `together`; anything else runs alone, in the model's order. A message steered in mid-run (`Control::steer`) cuts off the reply being written and asks again with it, keeping the text the user saw; during tools, a command they wait on moves to the background and rides along with that batch's results.
- **Pictures** (`wack-agent/src/images/`): a tool's `ToolOutput` can carry images, each with a `label` (what it shows) that is never sent; the wire formats place them differently (Chat Completions, whose tool messages are text only, gets them in a user message straight after the last tool message, labelled by call). `images::ingest` makes each picture a viewing copy (1568 px long edge, 1.5 MB, untouched when it fits, so screenshot coordinates hold) and saves the original (SHA-256-named, 0600) in the chat's `images/` folder, which gives it the `img:` id that `list_images` / `read_image` reopen. Each request's copy is trimmed in `images::prepare`: a model without vision is told the pictures were left out; otherwise everything after the model's last reply is always sent, and the oldest go six at a time past 20 pictures / 12 MB, each leaving a line naming it — the cut moves only forward, so the prompt cache breaks rarely. Compaction counts a picture as about 1,500 tokens and never sends it. The composer attaches up to eight (20 MB each) as `Job::Attached`; a message with pictures queues behind a run, never steers.
- **Deferred tools** (`registry.rs`): a tool is `Always` or `Deferred`. Anthropic's own endpoint gets deferred tools marked for its tool search; everywhere else the model gets our `tool_search`, and what it finds is added to the *end* of the tool list, so the cached start of the request never changes. The session records what was found, so a resumed chat offers the same tools. The ten core tools are always loaded; MCP, browser, canvas, computer use and web tools are deferred.
- **Sessions** (`session.rs`): one append-only JSON-lines file per chat; a rewind is one more line saying how much of the conversation still stands, and there are no branches. The user's messages are found by counting (`is_prompt`), the same way the transcript counts them. A `checkpoint` line before each of the user's messages names the tree of the chat's files then.
- **Compaction** (`compaction.rs`): at 80% of the model's context window, or when the provider refuses a request as too long. The model writes the summary's body; the user's own messages and the lists of files read and changed are carried in code.
- **The prompt** (`prompt.rs`): the profile's core text, a guide to this chat (date, folder, tool list), then `AGENTS.md` / `CLAUDE.md` from the working directory and every folder above it. Built once per run.
- **Features** hook in through `agent::Feature` (`on_run_start`, `notes`, `before_request`, `on_tool_call`, `after_turn`, `on_run_end`, `state_to_save`, `summary_sections`): compiled in, no extension runtime. A feature keeps its state in the session (`Entry::State`, latest per key, kept through compaction) and tells the model things through app notes (user-role messages the transcript hides and compaction never quotes as the user's words). A tool can end the run (`ToolSpec::ends_run`) or wait on the user (`ToolContext::user`, answered through `Control::answer`). The loop reports every model invocation to a `usage::Recorder` (`wack-agent/usage.rs`); the engine's ledger writer implements it, and title requests report through it too.
- **Shell tasks** (`wack-agent/src/tasks/`): every `bash` command is a task of the chat's `Tasks`, which the chat owns (not the run), so a server outlives the turn. There is no status tool: a task's end reaches the model as a note before its next request, or keeps the run going (`Feature::pending`); in an idle chat the app wakes it (`Agent::wake`) unless a plan or a queued message waits, the user stopped the last run, or it has woken three times since they last wrote. `wait_for_tasks` is the one bounded wait (270 s, once per reply). A task notices a local address in its output, so a server that serves moves to the background and its result carries the address; a task's end is reaped by polling as well as SIGCHLD, because Chromium's startup resets SIGCHLD's handler (`tests/sigchld.rs`).
- **Sub-agents** (`wack-agent/src/agents/`): the `agent` tool starts a child, a full `Agent` with its own session file beside the chat's; `agent_message` steers a working child or runs another round of an ended one. Roles are Markdown files with frontmatter; Explore, Review and General are built in, and the user's own replace them by name. A role without `write` and `edit` is no-edit: Plan mode lets only those run, and their `bash` is never policy-gated outside Plan mode, so builds and tests always work. At most six children run at once (the rest queue), sixteen start per user message, and one lock decides whether a child's report is its call's result or a note, so it reaches the model exactly once. `with_conversation` starts a copy of the parent (exact system prompt, tools and messages, so the prompt cache holds); children never get the agent tools (one level), questions, todos or the plan tools. A child's model requests reach the ledger as `purpose: subagent` with `subagent_id` `<chat>/<id>`.
- **Team** (`agents/team.rs`): the chat's model leads and a crew model does most of the reading and typing. Each `agent` call runs on a tier, `lead` or `crew` (the role's `team:` frontmatter; Review leads); a child keeps its tier through every round, and a copy of the conversation always runs on the lead's model. The contract is a note tagged `team:on` / `team:off` under the marker `[WACKCODE TEAM MODE v1]`, so the system prompt and tools are byte-identical with Team on or off. A fresh child starts with a briefing the app writes into its first message (so siblings on the crew share a cached prefix), and every child's report ends with the files the app saw it change (`## Files it changed`). Parallel edits are trusted to the prompt: there are no file leases.
- **Plan and Ultra Plan, questions, todos** (`plan/`, `ask.rs`, `todo/`, assembled by `kit.rs`): the mode contract is a note, re-sent only when the mode in force differs from the last one the model saw; while planning, a tool runs only if it changes nothing (`parallel_safe`) or, for `bash`, passes the shell policy (`plan/policy.rs`, fail-closed), unless Settings › Tools lifts that. `plan_mode_complete` ends the run with the plan saved as state `plan`; a new user message consumes it. The tool list and system prompt never change between modes, so the prompt cache holds. **Ultra** reasoning is `wack_core::Reasoning::Ultra`: the provider gets its maximum effort and the system prompt gains `prompt::ULTRA_PROMPT`; it never reaches `wack-llm`.
- **Task suggestions** (`suggest.rs`): `suggest_task` files a follow-up the run did not do — a bug, a rough edge, a missing bit of polish — with a title, a kind and a Markdown brief, five a run and never the same title twice. A started suggestion travels as a `<suggested-task-v1>` tail on the message, so restarts re-derive what was started. Start here queues behind a run; Start in new chat opens a background tab on the origin's model. Sub-agents never see the tool.
- **Memory** (`memory/`, the folder chosen by `wack-core/memory.rs`): `memory_save`, `memory_recall` and `memory_forget` work on one project's note files, keyed on the repository's common root so worktrees share them. The kit reads the index once per run and adds it to the system prompt after the project instructions; bodies never enter the prompt. Memory switched off means no folder for the run: no tools and no index. Plan mode lets the memory tools through.
- **Skills and slash commands** (`skills/`, `commands/`): skills are found in the roots the engine names, first name wins, a switched-off skill frees its name. The kit lists every skill the model may choose in the system prompt; the model loads one with `read`, so there is no skill tool. A leading `/name` is expanded in the engine before the run, the same for the app and `wack run`, and the session keeps what the user typed beside the expanded message. `/new`, `/name`, `/copy` and `/compact` act on the app and never reach the model.
- **MCP** (`wack-mcp`): hand-rolled JSON-RPC over stdio, Streamable HTTP and legacy SSE, tools only. The app owns one `Hub`; a connection is keyed by server, connection fingerprint and project folder, so every chat in a project shares it. Connections start lazily, stay up across runs, close after 30 idle minutes, wait five minutes after a failure, and are killed on quit. A run never waits for a server whose tool list it knows (live, or cached in `v3/mcp-cache/`); it waits only for one with none, and Stop ends the wait, not the connection. Tools are deferred, named `mcp__<slug>__<tool>`, read-only by the server's `readOnlyHint`, and checked against the live server before each call. A server that fails or stops is told to each chat using it once, as an `mcp:` note. Servers are scoped by area (Everywhere, Code only, Chat only) and, when Code is included, by project.
- **The browser** (`wack-browser`): one CEF for the whole app, its library loaded first thing in `main` (loading it swaps the process's allocator, which is unsafe once other threads run) but started only the first time a tab is shown or used, shut down when the app quits. Each tab's page is a native view of the window, parked off-screen (never hidden) when no pane shows it, so the agent drives and captures pages in the background; the agent's side is in-process DevTools. A chat owns its `ChatTabs` (`tabs.rs`), as it owns `Tasks` and `Agents`, behind a `Backend` the tests replace. `policy.rs` is the agent's address rule ([security.md](security.md)).
- **Computer use** (`wack-computer`): eight deferred `computer_*` tools that work in the user's other apps in the background, on a `Desktop` trait the tests fake (`native::desktop::Mac` is the real one). Every action climbs `ladder.rs` (Accessibility first and read back, raw input to the app's process only where the table allows), then the app is read until it holds still, and the answer says what changed. Pictures are one window, covered or not, sized so no provider rescales them. Access is per chat and per app, granted only from the card (`computer.rs`); the rules are in [security.md](security.md).
- **Canvases** (`wack-canvas`): a chat's canvases are files plus an index, never a fold over the session, and the agent revises them with exact `edits`. Three deferred tools, offered only to runs that have the browser engine and never to sub-agents, and allowed in Plan mode (they write only app data): `canvas_guide`, `canvas` and `canvas_look`. A `canvas` call waits for its artboards to be drawn and answers with a render report (size, overflow, console errors, the comments still open), so a broken board is caught without a screenshot. One `Renderer` (`render.rs`) draws for the board, `canvas_look` and export alike. Pages are offline ([security.md](security.md), "Canvas").
- **`wack-core/store.rs`** holds connections in `state.json` and their keys in `secrets.json`; `Store::provider` sends a key with the requests that need it, and `Store::reveal_connection_key` is the one path a key takes to the screen, for Settings › Providers' eye. A new chat pins its resolved connection and model (`Store::resolve_default`), while an existing chat (`Store::resolve`, `Store::resolve_chat`) never silently falls back to defaults or another connection: when its connection or model is removed or switched off, the chat stays readable, surfaces `MODEL_MISSING_MESSAGE`, and refuses prompts and compaction until another model is picked or the connection is switched back on.
- **The model catalogue** (`wack-catalog`, `wack-core/catalog.rs`): what models.dev knows that WackCode uses (context, max output, efforts, vision), per provider and per maker. The importer reads each entry on its own, so one odd value can't sink a refresh; only a feed with nothing usable is refused. A snapshot is built in (`cargo catalog`); Refresh writes a newer copy whole. A connection switched off stays stored with its key but is skipped by `Store::resolve`, the model menu and `wack run`.
- **Chat mode** (`ChatKind::Chat`): a chat with no project. `Store::run_setup` branches on the chat's kind, so the app and `wack run --chat` assemble the same run: the persona and a chat guide in place of instruction files (`prompt::chat_system`), and a tool registry built from an allowlist (`wack-agent/src/chat_kit.rs`) behind a guard that refuses anything else. Its rules are in [security.md](security.md#chats-scratchpad). `@` references to other Chat chats travel as a tail on the message (`chat_refs.rs`) that `read_chat` resolves by id. Ledger records carry `mode: "chat"`, a null project and the scratchpad as workspace. Chats of both kinds can be archived (`Chat::archived`), which takes them out of the lists and stops them running.

## The UI layer

- **`app.rs`** (`AppState`) owns the engine's `Store`, what is selected, and a `ChatSession` for every chat opened since launch; every change goes through its methods. **`chat.rs`** (`ChatSession`) is one chat's live state: its conversation, transcript items, composer and the run on Tokio, with runs numbered so a finished run's task can never touch the next one.
- **`actions.rs`** lists what the user can do as GPUI actions; `shell.rs` handles them by calling `AppState`, so views hold no handle on the app and gallery scenes stay inert.
- **`conversation.rs`** folds saved history and live events into turns; **`work.rs`** turns those into the rows the transcript draws (prose between steps, each run of steps settling to one sentence, `commit.rs`'s milestone rows, `changes_card.rs`'s per-turn Changes card); all are pure and tested.
- **`panes/`** is the pane system: `layout.rs` (each chat's two docks as a tree of weighted splits and tab stacks) and `solve.rs` (window size + tree → rectangles) are pure and property-tested: everything tiles exactly, the transcript never drops below 420 × 240 at any window the app allows, and the sidebar steps aside before a dock is clamped. `dock.rs` draws the result; `changes.rs`, `terminal.rs`, `run.rs`, `tasks.rs`, `agents.rs` and `browser.rs` are the panes. The Browser pane draws a placeholder; the page itself is a native view the engine places over it. Each chat owns its panes (`ChatPanes`), so they outlast switching chats, and its layout is saved to `state.json`.
- **The Canvas pane** (`panes/canvas/`, ⌘⇧K): a board of pictures in GPUI, never live pages, so panning and zooming never wait on Chromium; Play makes one artboard a live page, Present shows pictures over the whole window, export saves PNG, standalone HTML or PDF. Tweaks (`tweaks.rs`) move the agent's levers with no model call; the Comment tool (`comments.rs`) pins comments to elements from a picture's element map. Each turn that changed a canvas gets a card under its log (`canvas_card.rs`).
- **Terminals** run in the engine (`wack-core/terminal.rs`, on `alacritty_terminal`): a login shell in the project folder, its screen handed to the UI as a plain `Snapshot`. The UI paints the grid itself, with the ANSI colours as theme tokens.
- **The window** (`shell.rs`, `window_state.rs`) is a frame around panes: the sidebar, the *stage* holding the screen (a chat's transcript and bottom dock, a new chat, Settings), and, while a chat's right dock shows, the side panel beside it. The chat tabs sit in one glass tray across the title strip, the open one marked by a bead that slides between tabs (`motion::Bead`). Every edge keeps an 8-point gutter; the pane solver works in the frame's inner space, so its guarantees hold. The window remembers its last normal-mode size, position and display UUID across launches.
- **Appearance** is kept by the engine (`wack-core/appearance.rs`: light or dark, one of ten fixed themes, and a library of backdrop pictures) and turned into the theme by `theme::apply`. `backdrop.rs` draws the picture behind the whole window and `glass.rs` makes the panes thin, vibrant glass over it; the new-chat and welcome screens show it clear instead, fading to the glass when a chat opens. Text stays readable over the picture (`theme.rs`, `Theme::glass`); the user's dim is never overridden.
- **Planning in the window**: the composer's Build | Plan toggle (⇧Tab cycles Build, Plan, Ultra Plan) sets `Chat::mode`, the truth between runs; `conversation.rs` folds the session's `plan` and `todo` state, so everything reads the same after a relaunch. The composer's Send wears a ring of how full the context is; hovering it opens the context popover (`wack-agent/src/context.rs`), and a tab on the card holds a segment for each thing worth saying (elapsed time, todo count, a Team's crew, commands running, changed files, ⌘B). The question card (`question.rs`) comes first while it is open. Attachments (`attachments.rs`) accept pictures and UTF-8 text files, the latter folding into an `<attached-files>` tail the transcript shows as expandable chips. The plan card (`plan_card.rs`) is the transcript's hero item; only the plan still awaiting review has actions. Ultra's look (`ultra.rs`) is a fixed prism in the theme, never the accent.
- **A chat's title and menu** (`context_menu.rs`): Rename (a title, a tab or a sidebar row), Reveal in Finder (or the scratchpad), Reveal chat file, Copy path, Close tab and Archive.
- **Rewinding, editing and retrying** (`rewind.rs` draws it, `wack-core/rewind.rs` and `checkpoints.rs` do it): under each of the user's messages, Copy, Edit, Rewind and, on the latest, Retry; a rewind puts the message's words back in the composer and leaves an Undo row at the transcript's end. Before each message the user sends, the run snapshots the chat's folder into `v3/checkpoints/<chat>/`, and a restore never writes over what the snapshot does not hold. Only while the chat is idle; nothing runs while a rewind writes the chat's file. Forking stays cut.
- **Two areas, Code and Chat** (`AppState::area`, ⌥⌘1 / ⌥⌘2, each area parking its own selection and tabs): the Chat area's chats draw as a messenger (`chat_transcript.rs`, over the same `conversation.rs` fold): time dividers, bubbles, activity chips that fold, the scratchpad files a reply wrote, typing moods and a jump-to-latest pill. Sidebar search and the Archived view serve both areas.
- **Motion** is in one place, `motion.rs`, and everything follows macOS's Reduce Motion, read at launch and whenever the window comes forward: arrivals on a critically damped spring, dock panes sliding in from their edge, the tab bead stretching to the next tab, the composer's lift and glint, and each Settings section's own little animated picture (`stage.rs`), which plays its story three times then holds still.
