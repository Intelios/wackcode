# Architecture

WackCode 3 is one Rust process. There is no Node worker, no IPC protocol and no web UI. The browser adds Chromium's own helper processes through CEF, which is why the app runs from a bundle ([cef.md](cef.md)).

## Crates

```
apps/wackcode      the app binary: opens the window, hands it to wack-ui
apps/gallery       renders UI scenes to PNG files
apps/wackcode-helper  CEF's helper processes (renderer, GPU, utility), copied into the bundle
apps/xtask         assembles the .app bundles: `cargo dev`, `cargo xtask bundle`
crates/wack-ui     views, pane tree, layout solver, theme        (GPUI)
crates/wack-core   engine: projects, chats, settings, secrets, Git, PTYs, events
crates/wack-agent  turn loop, tool registry, prompt assembly, sessions, compaction
crates/wack-tools  read, write, edit, bash, grep, find, ls
crates/wack-web    web_fetch (and web_search), and the guard that keeps them on the public internet
crates/wack-browser  the browser engine: Chromium through CEF, each chat's tabs, the agent's address policy
crates/wack-canvas  canvases: the agent's HTML artboards, drawn offline by the browser engine; their tools, tweaks and comments
crates/wack-computer  computer use: the agent in the user's other Mac apps, through Accessibility, window pictures and input; its access rules
crates/wack-mcp    the MCP client: servers as deferred tools, connections shared per project
crates/wack-llm    provider wire formats, streaming events, usage, retries
crates/wack-catalog  the model catalogue: context, max output, efforts and vision from models.dev, bundled and refreshable
crates/wack-cli    `wack`: the agent without the app
```

Dependencies point downwards only: `wack-ui` → `wack-core` → `wack-agent` → `wack-llm`, with `wack-tools`, `wack-web` and `wack-mcp` beside the agent. `wack-browser` sits beside them too: `wack-core` hands a chat's `ChatTabs` to every run, and `wack-ui` lends the engine the window's view. `wack-canvas` sits on `wack-browser` and `wack-agent` the same way: a chat owns its `Canvases`, and `wack-core` hands them to every run. `wack-computer` sits beside them on `wack-agent`: the app owns one `Computer`, each Code chat owns its `ChatComputer` (grants, the access card), and `wack-core` hands it to the chat's runs. `wack-catalog` depends on nothing of ours: `wack-core/catalog.rs` keeps it on disk and fills model rows from it.

## The one boundary that matters

**Nothing below `wack-ui` may depend on GPUI.** The UI is a viewport onto the engine: it calls typed async commands and subscribes to typed event streams. That keeps the choice of UI framework confined to one crate, and it is why the agent can run and be tested with no window at all (`wack-cli`).

The engine runs on Tokio. `gpui_tokio` bridges the two, so a view can await engine work.

State lives in models, not views. Closing a pane or switching a tab must never lose a terminal's scrollback or a diff's selection.

## Where data lives

```
~/Library/Application Support/com.wackcode.desktop/     (.dev for the dev app)
  usage/v1/...              the TokenTrail ledger: a published contract, see wackcode-usage-v1.md
  v3/state.json             projects, chats, settings
  v3/secrets.json           API keys, mode 0600
  v3/sessions/<chat>.jsonl  one append-only file per chat
  v3/sessions/<chat>/<id>.jsonl  each of the chat's sub-agents (a1, a2…), removed with the chat
  v3/tasks/<chat>/<id>.log  output of the commands the agent ran in the background (removed with the chat)
  v3/canvases/<chat>/<id>/  one canvas: canvas.json (its index), each artboard's HTML, assets/, comments.json, view.json (where the board's camera was left), renders/ (pictures, thumbnails, reports); removed with the chat
  v3/backgrounds/           backdrop images
  v3/memory/<label>-<key>/  one project's memory notes (Markdown with frontmatter), origin.json, .trash/
  v3/memory/chat-c4a7c4a7c4a7/  the one memory store every Chat chat shares
  v3/scratch/<chat>/        a Chat chat's scratchpad, its only working folder (mode 0700, removed with the chat)
  v3/chat-area/             the one empty folder Chat chats' MCP servers start in
  v3/commands/<name>.md     the user's own slash commands (Settings › Commands)
  v3/agents/<name>.md       the user's own sub-agent roles (Settings › Sub-agents); the only agent folder WackCode writes to
  v3/web-usage.json         Settings › Web's monthly count of searches and page reads per provider
  v3/mcp-cache/<sha256>.json  each MCP server's last tool list, named by its connection's fingerprint (7 days)
  v3/model-catalog.json     the model catalogue as last refreshed from models.dev; used while newer than the built-in snapshot
~/.agents/skills/           the user's skills, shared with other tools; the only skill folder WackCode writes to
```

Version 3 keeps everything of its own under `v3/` and never reads or writes version 2's files, which share the same folder. Skills also load (read-only) from other tools' folders the user switches on (`~/.claude/skills`, `~/.codex/skills`, `~/.config/opencode/skills`) and folders they add; a project's own skill folders are never read. Sub-agent roles likewise load from Claude Code's `~/.claude/agents` when the user switches it on, read-only, and never from a project.

## The agent core

Each file's header comment states its invariants; this is the map.

- **`wack-llm`** turns one internal `Request` into three wire formats (`anthropic.rs`, `responses.rs`, `chat.rs`) and their event streams back into one `Response`. Blocks a provider needs back unchanged (thinking signatures, encrypted reasoning, its own tool-search blocks) are kept as `Opaque` and replayed only to the format that made them. `retry.rs` retries rate limits, overload and network failures, never once any text has reached the user. `testing.rs` has the scripted provider every test above this crate uses. A request's `output_limit` is the model's max output: never sent on its own, it caps whatever is asked for, so Anthropic's 32k default and compaction's 8k never exceed a model that writes less. `HttpProvider::list_models` reads the provider's own model list for Fetch models.
- **`wack-agent/agent.rs`** is the turn loop. Every tool call gets exactly one result in the next message, whatever happens (refused, failed, stopped). Calls that only read run side by side, as do calls whose tool is marked `together` (the sub-agent tools); anything else runs alone, in the model's order. A message sent mid-run rides along with the next tool results.
- **Pictures in tool results** (`tool.rs`, `images.rs`): a tool returns a `ToolOutput`, text plus optional images (a screenshot), and `Block::ToolResult` carries them; each picture has a `label` of our own (what it shows), never sent. Anthropic gets them inside the `tool_result`, Responses as `input_image` items in the call's output, and Chat Completions, whose tool messages are text only, in a user message straight after the last tool message, each labelled with its call. A turn's results keep at most 20 pictures and 12 MB (`images::cap_turn`, saying what was cut). The session keeps every picture as it came; each request's copy is trimmed in `images::prepare`: a model whose `accepts_images` is off (`wack-core`'s `Model`, on unless saved otherwise) gets a line saying the pictures, the user's included, were left out. Otherwise every picture after the model's last reply is always sent (the turn's results, the user's message, and any note the app saved after them), since the model has not seen them (eliding a batch it just asked for traps it in taking it again: version 2's loop), and older ones, the user's and the tools' alike, while the request stays within 20 pictures and 12 MB; past that the oldest are elided six at a time, each leaving a line naming what it was and that the model saw it. The cut moves only forward and only in those steps, so the prompt cache breaks rarely. Before any of that, `images::ingest` (at the one place a tool's output becomes a result) turns every picture into its viewing copy (`images/view.rs`: at most 1568 px on the long edge and 1.5 MB, untouched when it already fits, so screenshot coordinates hold) and saves its original in the chat's `images/` folder beside its sub-agents' sessions (`images/store.rs`, named by SHA-256, 0600), which gives the picture its `id`; sub-agents share their chat's. `read` returns picture files, MCP results their images, and the deferred `list_images` / `read_image` (`images/tools.rs`) reopen any picture of the conversation by its `img:` reference, which the elision line names. A model without vision is told `read` found a picture and is refused screenshots; Settings › Providers has a Vision switch per model. Compaction counts a picture as about 1,500 tokens and tells the summariser it was there, never sends it; the user's carried words name their attached pictures by reference. The user attaches pictures in the composer (paste, a drop from the Finder or its attach button; `wack-ui/src/attachments.rs`: eight to a message, 20 MB each, anything readable converted to PNG); they travel as `Job::Attached` to `Agent::run_with`, which saves and ingests them like a tool's, after the text. A message with pictures queues behind a run, never steers; a model without Vision holds Send with a line saying why. The transcript shows pictures (`wack-ui/src/pictures.rs`): the user's above their bubble, a tool's under its work-log row (`Event::ToolResult` carries the viewing copies), and those a reply names with `![…](img:…)` under the reply, looked up among the conversation's saved pictures. They decode once, off the main thread, into a shared cache; a click opens the lightbox (fitted or at its own size, stepping through its strip, Esc or a click outside closes it), drawn in GPUI's overlay plane so it covers browser pages. A reply may name a picture by its `img:` reference or by the path it was read from. Chat Completions labels each tool picture with its call and its label (a file's path), since a model given only call ids mixed up a batch. Checked against the Testing connection on 2026-11-18: GLM-5.3-Flash read three and then twelve PNGs at once and named their colours (two swapped of twelve). A second twelve elided the first batch's oldest, and it answered from what it had seen without reading again (two replies). In the dev app, a read picture showed in the reply after a relaunch and opened in the lightbox (a click on its backdrop reached nothing beneath); two `browser_batch`es of twelve screenshots each reached the model whole, answered in one reply with nothing taken again; with Vision off, `read` told the model it can't view the picture. Not yet run live: attaching by paste, drop or the picker (unit tests and the `composer-attachments` scene only), and the Anthropic and Responses formats with pictures (recorded-stream tests only).
- **Deferred tools** (`registry.rs`): a tool is `Always` or `Deferred`. Anthropic's own endpoint gets deferred tools marked for its tool search. Everywhere else the model gets our `tool_search`, and what it finds is added to the *end* of the tool list so the cached start of the request never changes. The session records what was found, so a resumed chat offers the same tools. The ten core tools (the seven in `wack-tools` and the three for background commands) are always loaded; MCP, browser, canvas, computer use and web tools will be deferred.
- **Sessions** (`session.rs`): one append-only JSON-lines file per chat, linear. Opening one drops a cut-off last line and answers any tool call a crash left unanswered.
- **Compaction** (`compaction.rs`): at 80% of the model's context window (when the connection states one), or when the provider refuses a request as too long. The model writes the summary's body; the user's own messages and the lists of files read and changed are carried in code.
- **The prompt** (`prompt.rs`): the profile's core text, a guide to this chat (date, folder, tool list), then `AGENTS.md` / `CLAUDE.md` from the working directory and every folder above it. Built once per run.
- **Features** hook in through `agent::Feature` (`on_run_start`, `notes`, `before_request`, `on_tool_call`, `after_turn`, `on_run_end`, `state_to_save`, `summary_sections`): compiled in, no extension runtime. A feature keeps its state in the session (`Entry::State`, latest per key, kept through compaction) and tells the model things through app notes (user-role messages the transcript hides and compaction never quotes as the user's words). A tool can end the run (`ToolSpec::ends_run`) or wait on the user (`ToolContext::user`, answered through `Control::answer`). Separately, the loop reports every model invocation to a `usage::Recorder` (`wack-agent/usage.rs`): one report per invocation, with its purpose, duration, outcome and counts; the engine's ledger writer implements it, and title requests report through it too.
- **Shell tasks** (`tasks/`): every `bash` command is a task of the chat's `Tasks`, which the chat owns (not the run), so a server outlives the turn. A foreground command is a task the call waits on; when the model asks (`run_in_background`), its timeout passes (120 s by default: it moves, it is not killed) or the user presses ⌘B, it carries on in the background and its result tells the model, once, everything it needs. There is no status tool: a task's end (and each batch of a `watch`'s lines) reaches the model as a note before its next request, or, when the reply was the last, keeps the run going (`Feature::pending`). In an idle chat the app wakes it (`Agent::wake`, `Job::Wake`) unless a plan or a queued message waits, the user stopped the last run, or it has woken three times since they last wrote. `stop_task` only stops; `wait_for_tasks` is the one bounded wait (270 s, once per reply). Stopping a run kills only its foreground command. The session's `tasks` state lets the next run say which tasks a quit killed.
- **Sub-agents** (`agents/`; settings and roles' folders in `wack-core/agents.rs`): the `agent` tool starts a child, a full `Agent` with its own session file beside the chat's, and `agent_message` steers a working child or runs another round of an ended one with its role's current rules. Roles are Markdown files with frontmatter (`name`, `description`, `tools`, `model: helper|chat`, `max_turns`): Explore, Review and General are built in (`agents/builtin/`), the user's own replace them by name, first name wins. A role without `write` and `edit` is no-edit: Plan mode lets only those run, and their `bash` is never policy-gated outside Plan mode, so builds and tests always work. The chat owns its `Agents` registry, as it owns `Tasks`: at most six run at once (the rest queue), sixteen start per user message, and one lock decides whether a child's report is its call's result or a note, so it reaches the model exactly once. A background child's report wakes an idle chat (outside the three-wake cap, which the spawn budget replaces); one from a round the user started in the Agents pane rides along quietly. `with_conversation` starts a copy of the parent: its exact system prompt, tools and messages, so the prompt cache holds, with the parent's open calls answered and a directive added. Children never get the agent tools (one level), questions, todos or the plan tools; Esc stops every child, ⌘B moves the waited-on ones to the background, and a child working at quit reads as Interrupted after a relaunch, which the model is told it can continue. A child's model requests reach the ledger as `purpose: subagent` with `subagent_id` `<chat>/<id>`; no-edit roles run on Settings › Sub-agents' helper model when one is chosen.
- **Team** (`agents/team.rs`; the crew in `wack-core/agents.rs`): the chat's model leads and a crew model does most of the reading and typing. Team on is a crew set on the chat (`Chat.team`, a `ModelChoice`), resolved into `AgentsSetup::crew` for the run; a crew that no longer resolves holds Send with a line saying why and is never swapped for the lead's model, and Delegation Off leaves Team unavailable. A new Team starts on the default crew, else the helper model, else the first model on a connection that is on, never the lead's own when another exists. Each `agent` call runs on a tier, `lead` (the chat's model) or `crew`: its `model` input, else the role's `team: lead|crew` frontmatter (crew when absent; Review leads, so the strong model judges the change). Outside Team, `crew` means the helper model. A child keeps its tier through every round, and a copy of the conversation always runs on the lead's model, so the parent's cache holds. The contract is a note tagged `team:on` / `team:off` under the marker `[WACKCODE TEAM MODE v1]` (never `contract:`, which is Plan's), so the system prompt and tools are byte-identical with Team on or off; it is re-sent when its text changes or a compaction drops it, and `team:off` only while the model can still see `team:on`. Its body is a method, not "delegate everything": size the work, understand before splitting, decide the shape, brief like a spec, split by file, review every change, send work back at most twice, finish yourself; Settings › Prompts edits it as Team lead. A fresh child of a Team chat starts with a briefing the app writes into its first message (never its instructions, so siblings on the crew share a cached prefix): the user's request, the approved plan or the lead's todo list, who else is working on which files, and its own `files`. Every child's report ends with the files the app saw it change through `write` and `edit` (`## Files it changed`, those outside its `files` marked), above the footer the UI parses. Parallel edits are trusted to the prompt: no file leases and no engine-run checks (the owner's call, 2026-11-26). The registry also remembers which children the latest message started (`Agents::this_message`), which the UI counts.
- **Plan and Ultra Plan, questions, todos** (`plan/`, `ask.rs`, `todo/`, assembled by `kit.rs`), ported from version 2 with its prompts: the mode contract is a note, re-sent only when the mode in force differs from the last one the model saw; while planning, a tool runs only if it changes nothing (`parallel_safe`) or, for `bash`, passes the shell policy (`plan/policy.rs`, fail-closed), unless Settings › Tools lifts that. `plan_mode_complete` ends the run with the plan saved as state `plan`; a new user message consumes it. The tool list and system prompt never change between modes, so the prompt cache holds. **Ultra** reasoning is `wack_core::Reasoning::Ultra`: the provider gets its maximum effort and the system prompt gains `prompt::ULTRA_PROMPT`; it never reaches `wack-llm`.
- **Task suggestions** (`suggest.rs`, the card under a settled turn in `suggestion.rs`), ported from version 2: `suggest_task` files a follow-up the run did not do — a bug, a rough edge, a missing bit of polish — with a title, a kind and a Markdown brief, five a run and never the same title twice (the saved `suggestions` state survives restart and compaction). A started suggestion travels as a `<suggested-task-v1>` tail on the message, which the transcript splits off (never shown, a caption says what it was) so restarts re-derive what was started; `suggestion_view` reads the rest from the store — dismissals on the chat, opened chats from `Chat::origin`, queued sends from the send queue — so deleting a started chat frees its card. Start here queues behind a run; Start in new chat opens a background tab on the origin's model; the chevron offers Plan and Ultra Plan in either place and Copy as prompt. Sub-agents never see the tool.
- **Memory** (`memory/`, the folder chosen by `wack-core/memory.rs`), ported from version 2 with its tool texts: `memory_save`, `memory_recall` and `memory_forget` work on one project's note files, keyed on the repository's common root so worktrees share them. The kit reads the index once per run and adds it to the system prompt after the project instructions and before Ultra; bodies never enter the prompt. Memory switched off (Settings › Memory, globally or per project) means no folder for the run: no tools and no index. Plan mode lets the memory tools through. Version 2's notes are not imported.
- **Skills and slash commands** (`skills/`, `commands/`; folders and switches in `wack-core/skills.rs`), ported from version 2's rules: skills are found in the roots the engine names, first name wins, a switched-off skill frees its name. The kit lists every skill the model may choose (name, description, file) in the system prompt, read once per run; the model loads one with `read`, so there is no skill tool. A leading `/name` is expanded in the engine (a skill's `<skill>` block, a template's `$1`/`$ARGUMENTS`, `/init`'s prompt) before the run, the same for the app and `wack run`, and the session keeps what the user typed beside the expanded message (`Entry::Message::command`) so the transcript shows `/name · args`. `/new`, `/name`, `/copy` and `/compact` act on the app and never reach the model.
- **MCP** (`wack-mcp`, settings in `wack-core/mcp.rs`): hand-rolled JSON-RPC over stdio, Streamable HTTP and legacy SSE, tools only. The app owns one `Hub`; a connection is keyed by server, connection fingerprint and project folder (a stdio server's working directory), so every chat in a project shares it. Connections start lazily, stay up across runs, close after 30 idle minutes, wait five minutes after a failure, and are killed on quit (`AppState::shutdown_runs`). A run never waits for a server whose tool list it knows (live, or cached in `v3/mcp-cache/`); it waits only for one with none, and Stop ends the wait, not the connection. Tools are deferred, named `mcp__<slug>__<tool>`, read-only by the server's `readOnlyHint`, and checked against the live server before each call. A server that fails or stops is told to each chat using it once, as an `mcp:` note the transcript shows. A server can be limited to chosen projects. `wack run` makes a hub of its own; `wack mcp list|test`.
- **The browser** (`wack-browser`): one CEF for the whole app, its library loaded first thing in `main` (loading it swaps the process's allocator, which is unsafe once other threads run) but started only the first time a tab is shown or used, pumped from the main dispatch queue (`main_thread.rs`), shut down when the app quits. Each tab's page is a native view of the window, parked off-screen (never hidden) when no pane shows it, so the agent drives and captures pages in the background. The agent's side is in-process DevTools: `cdp()` answers through a oneshot, and the page's events fold into `TabState` (`state.rs`): address, title, loading, a dialog held for an answer, and console and network ring buffers labelled by page, which outlive navigations. A chat owns its `ChatTabs` (`tabs.rs`), as it owns `Tasks` and `Agents`, behind a `Backend` the tests replace: opening the address already shown is not a reload, a popup becomes a tab of the same chat and owner with `window.opener` kept, an agent's tab is the agent's from its first load, and saved tabs make no page until used. `policy.rs` is the agent's address rule (docs/security.md).
- **Computer use** (`wack-computer`): eight deferred `computer_*` tools that work in the user's other apps in the background, on a `Desktop` trait the tests fake (`native::desktop::Mac` is the real one). Accessibility runs on one thread per app (`engine.rs`); an AX walk reads each element in one message; refs are stable per app for as long as the element exists. Every action climbs `ladder.rs` (Accessibility first and read back, raw input to the app's process only where the table allows), then the app is read until it holds still, and the answer says what changed (`change.rs`). Pictures are one window, covered or not, sized so no provider rescales them (`geometry::budget`). Access is per chat and per app, granted only from the card (`computer.rs`); the rules are in docs/security.md. The crate header records what the Phase 0 spike found works in the background.
- **Canvases** (`wack-canvas`): a chat's canvases are files plus an index, never a fold over the session, and the agent revises them with exact `edits`. Three deferred tools, offered only to runs that have the browser engine and never to sub-agents, and allowed in Plan mode (they write only app data): `canvas_guide` (the guide, with Claude Design's craft points), `canvas` (add, revise, remove, tweaks, `resolve_comments`) and `canvas_look`. A `canvas` call waits for its artboards to be drawn and answers with a render report (size, overflow, console errors, the comments still open), so a broken board is caught without a screenshot. One `Renderer` (`render.rs`) draws for the board, `canvas_look` and export alike: a page at the artboard's CSS size, a PNG at 2x (at most 8 MP) and a thumbnail, one drawing at a time behind a watchdog, auto heights measured from the content's boxes. `runtime.js`, put at the top of every page, applies tweaks and measures the page, including a map of its visible elements that comments point into. Pages are offline (docs/security.md). `CanvasFeature` writes the notes: tweaks the user moved, comments they sent with their message (armed when that message starts the run, told in the note before it, flagged in `comments.json` until then), and the canvas list for a compaction's summary.
- **`wack-core/store.rs`** holds connections in `state.json` and their keys in `secrets.json`; `Store::provider` sends a key with the requests that need it, and `Store::reveal_connection_key` is the one path a key takes to the screen, for Settings › Providers' eye. `Store::draft_provider` gives Fetch models a provider for the connection being edited: a typed key, or the saved one only at the saved address's origin. A new chat pins its resolved connection and model (`Store::resolve_default`), while an existing chat (`Store::resolve`, `Store::resolve_chat`) never silently falls back to defaults or another connection: when its connection or model is removed or switched off, the chat stays readable, surfaces `MODEL_MISSING_MESSAGE`, and refuses prompts and compaction until another model is picked or the connection is switched back on.
- **The model catalogue** (`wack-catalog`, `wack-core/catalog.rs`): what models.dev knows that WackCode uses (context, max output, whether a model reasons and its efforts, vision, release date), per provider and per maker. The importer reads each entry on its own and never reads API formats or endpoints, so one odd value can't sink a refresh as it did in version 2; only a feed with nothing usable is refused. A snapshot is built in (`cargo catalog` regenerates it); Refresh writes a newer copy whole. Search ranks the provider at the connection's address first, under its own ids; elsewhere the makers' records answer under bare ids, with borrowed efforts marked. A connection switched off stays stored with its key but is skipped by `Store::resolve`, the model menu and `wack run`.

- **Chat mode** (`ChatKind::Chat`, ported from version 2): a chat with no project. `Store::run_setup` branches on the chat's kind, so the app and `wack run --chat` assemble the same run: version 2's persona and a chat guide in place of instruction files (`prompt::chat_system`), a tool registry built from an allowlist (`wack-agent/src/chat_kit.rs`: the file tools confined to the scratchpad, web, browser, canvas, MCP, memory, questions, pictures and `read_chat`) behind a guard that refuses anything else, and always Build. Its rules are in [security.md](security.md#chats-scratchpad). `@` references to other Chat chats travel as a tail on the message (`chat_refs.rs`) that `read_chat` resolves by id. Ledger records carry `mode: "chat"`, a null project and the scratchpad as workspace. Chats of both kinds can be archived (`Chat::archived`), which takes them out of the lists and stops them running.

## The UI layer

- **`app.rs`** (`AppState`) owns the engine's `Store`, what is selected, and a `ChatSession` for every chat opened since launch. Every change goes through its methods.
- **`chat.rs`** (`ChatSession`) is one chat's live state: its conversation, the transcript items built from it, its composer, and the run on Tokio. Runs are numbered so a finished run's task can never touch the next one.
- **`actions.rs`** lists what the user can do as GPUI actions. Views dispatch them; `shell.rs` handles them by calling `AppState`, so views hold no handle on the app and gallery scenes stay inert.
- **`conversation.rs`** folds saved history and live events into turns; **`work.rs`** turns those into the rows the transcript draws, lifting `git commit` calls out into standalone milestone rows (`commit.rs`) that break work groups and summarising each settled turn's edited or created files in a Changes card (`changes_card.rs`); all are pure and tested.
- **`panes/`** is the pane system. `layout.rs` is a chat's two docks (the side panel right of the stage, and the bottom of the stage under the transcript) as a tree of weighted splits and tab stacks; every pane opens as a tab of the right dock, as version 2's side panel did, and the bottom dock holds only what the user drags there; `solve.rs` turns the window size and that tree into rectangles for the sidebar, the title strip, the transcript, the gap before the side panel and every stack. Both are pure and property-tested: everything tiles exactly, the side panel runs the frame's full height, the transcript never drops below 420 × 240 at any window the app allows (700 × 480 and up), and the sidebar steps aside before a dock is clamped. `dock.rs` draws the result: the side panel's stacks in a pane of their own, the bottom dock's inside the stage, and the lines and drop zones over both, with every stack's tabs as pills; `changes.rs`, `terminal.rs`, `run.rs`, `tasks.rs`, `agents.rs` and `browser.rs` are the panes. The Browser pane draws a placeholder; the page itself is a native view the engine places over it from presentation callbacks (`crate::browser`: the shell paints a mark first and last, so a page whose pane did not paint is parked), and keyboard focus moves between the app and a page in the engine's `sendEvent:` shim: a press gives the keyboard to the page under it (and the pane the app's focus, through `cef::on_page_press`), a press elsewhere or the app's focus leaving the pane takes it back, and a page never takes it by loading. The New chat screen's panes own tabs of their own until the first message, whose chat takes them over live. Each chat owns its panes (`ChatPanes` in `ChatSession`), so they outlast switching chats, and its layout is saved to `state.json` shortly after it changes.
- **The Canvas pane** (`panes/canvas/`, ⌘⇧K, the title strip's Canvas word): a board of pictures in GPUI, never live pages, so panning and zooming never wait on Chromium. It opens at most of the stage (`Layout::canvas_width`, set only by the user; the transcript keeps its minimum) and follows the agent's changes without ever zooming in. Play makes one artboard a live page, placed exactly over its picture and shown only while wholly inside the pane; Present shows pictures over the whole window; export saves PNG, standalone HTML or PDF. Tweaks (`tweaks.rs`) move the agent's levers with no model call, live on a playing page; the Comment tool (`comments.rs`) pins comments to elements from a picture's element map, and the composer's chip says they go with the next message. Each turn that changed a canvas gets a card under its log (`canvas_card.rs`).
- **Terminals** run in the engine (`wack-core/terminal.rs`, on `alacritty_terminal`): a login shell in the project folder, its screen handed to the UI as a plain `Snapshot`. The UI paints the grid itself, with the ANSI colours as theme tokens.
- **The window** (`shell.rs`, `window_state.rs`) is a frame around panes, after Zeron: the sidebar, the *stage* holding the screen (a chat's transcript and bottom dock, a new chat, Settings), and, while a chat's right dock shows, the side panel beside it from the frame's top to its foot, as version 2's was. The chat tabs sit in one glass tray across the title strip over the stage, the open one marked by a bead that slides between tabs (`motion::Bead`); the side panel's top tabs sit on the same line. A chat's stage opens with its header: the title, project and branch, Build and Run, and the pane toggles. Every edge keeps an 8-point gutter; the pane solver works in the frame's inner space (`shell::solver_space`, `shell::to_solver`), so its guarantees hold and the window's minimum is the solver's plus the gutters. The window remembers its last normal-mode size, position and display UUID across launches (`Ui::window` in `state.json`, debounced during drags, flushed on quit, skipped while fullscreen, and clamped on launch to live monitors' visible bounds).
- **Appearance** is kept by the engine (`wack-core/appearance.rs`: light or dark, one of WackCode 2's ten themes by name, and a library of backdrop pictures, at most one shown, each with its blur, dim, texture, focus, zoom and the theme it brings back, plus optional shuffle-on-open and shuffle-now across the library) and turned into the theme by `theme::apply`. A chosen picture is copied into `v3/backgrounds/` as WackCode's own JPEG, with a small blurred copy beside it, so the original can move. **`backdrop.rs`** draws it behind the whole window, blurred and dimmed exactly as the user chose (a heavy blur starts from the blurred copy so the GPU does less), and the panes are thin, vibrant glass over it, as version 2's were (`glass.rs`): each paints a copy of the picture, its colour boosted in memory (`backdrop::vibrant`) and blurred exactly as the user chose, the glass adding no softness of its own (Blur at None shows the picture sharp through the panes, as behind version 2's chats), under the user's dim and a fill tinted towards the accent, and catches the light with a sheen, a bright top edge and a soft shadow; until that copy is ready a pane blurs live. On the new-chat and welcome screens the whole stage shows it clear and undimmed instead, optionally through a texture (Dither, ASCII, Halftone, Scanlines, after Zeron), with its smaller words on frosted pills and the display line ringed by a faint halo, nothing laid over the picture; when a chat opens it fades away to the glass, and back on New chat (`motion::Ease`). Textures are made once per picture off the UI thread. The picture is placed in Settings › Appearance's Position editor, a miniature of the window with the sidebar and composer outlined: dragging moves it with the pointer while the whole window follows, and a slider zooms from 100 to 400% about the middle (`backdrop::pan`, `zoom_focus`). The transcript fades out at its edges with the fork's edge fade (`edge_fade.rs`), so nothing paints a band across the glass. Text stays readable over the picture as in WackCode 2: each picture is measured on import for how dark and light its softened copy gets, and the theme moves the quieter steps of ink towards the loud end by one shared amount (keeping their order) until each clears a floor on the glass over the worst part, thickening the glass past its thinnest only when that is not enough (`theme.rs`, `Theme::glass`). The user's dim is never overridden.
- **Planning in the window**: the composer's Build | Plan toggle (⇧Tab cycles Build, Plan, Ultra Plan) sets `Chat::mode`, the truth between runs; `conversation.rs` folds the session's `plan` and `todo` state, so the mode in force, the plan awaiting review and the todo list read the same after a relaunch. The composer (`composer.rs`, one composer everywhere) reads as version 2's: attach, model with its connection's mark, effort, then the mode track beside Send, which wears a ring of how full the context is; hovering the ring (never clicking it) opens version 2's context popover, every part of the prompt with its share (`wack-agent/src/context.rs` estimates each part of the request the agent would send next and scales them to the measured total; the run sends them as `RunEvent::Context` as it ends). Inside the card's top a status line says what a run is doing and for how long, with the todo list's count; a tab on the card's edge holds what outlives a run, commands still running and the project's changed files (`ChatSession::changes`, counted by Git off the UI thread). Messages written while the agent works wait above the card as faint bubbles with Steer now, Edit and Remove. The todo list (`todo_panel.rs`) and the commands open above the card, in a column capped so some transcript always shows. The question card (`question.rs`) comes first: while it is open the status line and the tab only report. Attachments (`attachments.rs`) accept both pictures (PNG/JPEG/GIF/WebP or convertible clipboard images, up to 8 × 20 MB) and UTF-8 text files (picked, dropped, ≥32 KB pastes, or Terminal "Add selection to draft" via the floating pill and right-click context menu, sharing one 8-file / 256 KB per file / 512 KB total budget): text files fold into an attribute-escaped, line-counted `<attached-files>` tail that the transcript shows as expandable chips. The plan card (`plan_card.rs`) is the transcript's hero item; only the plan still awaiting review has actions. Ultra's look (`ultra.rs`) is a fixed prism in the theme, never the accent.
- **Two areas, Code and Chat** (`AppState::area`, saved in `Ui::area`): the pill in the sidebar's strip (⌥⌘1, ⌥⌘2) switches between them, and each area parks its own selection and tabs. The Chat area's sidebar groups chats by recency (`chat_area.rs`), its new chat is the hero (greeting, three ideas, the duck), and its chats draw as a messenger (`chat_transcript.rs`, over the same `conversation.rs` fold): time dividers, bubbles, plain-words activity chips that fold, the scratchpad files a reply wrote, typing moods and a jump-to-latest pill. Sidebar search and the Archived view serve both areas.
- **Motion** is in one place, `motion.rs`: arrivals on a critically damped spring (screens, menus, a settings section), dock panes sliding in from their edge, the area hop (the sidebar's page and the stage arrive from the switch's side), the open tab's bead stretching to the next tab and gathering up behind it (`Bead`), the side panel sliding in as its glass frosts, a light crossing a working tab and running along "Working", work-log marks landing on the rail and the step under way breathing, the composer's lift and glint as a message leaves, and the working duck's stepped paddle. Copy buttons (`copy.rs`) turn into a check for a beat; a todo's tick pops in; a new chat's sidebar row grows into place; a reply's newest words arrive tinted and settle into ink; a light runs along "Thinking". Opening or closing Settings rebuilds the window as version 2 did (`motion::rebuild`: the sidebar flies in from the left, the rows, strip and page settle in a stagger), and the sidebar slides open and shut with the panes gliding beside it (`Solution::sliding`). Each Settings section's own page opens with a little animated picture of what it is for, after version 2's (`stage.rs`, beside the head from `settings_kit::staged_head`): it plays its story three times, then holds still, so an open page redraws nothing. Everything follows macOS's Reduce Motion, read at launch and whenever the window comes forward.
